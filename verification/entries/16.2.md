## Task 16.2: End-to-end integration tests
Requirements: 10.7, 14.1, 14.2, 14.3, 14.4, 16.3
### Changes
- `tests/integration/test_end_to_end.py` (new, 21 tests). The module is skipped with a message naming `scripts/build_decoder.sh` when `build/decoder/ScanTape` is missing or not executable, the same pattern as `test_clean_uef.py`. A module-scoped fixture hashes the five inputs (`clean.wav`, `damaged_a.wav`, `damaged_b.wav`, `reference_payloads.json`, `damage.json`) and then decodes the three WAVs with the real patched decoder through `decode_capture`. CLI tests run `[sys.executable, "-m", "taperescue.cli", ...]` as a subprocess with `--decoder build/decoder/ScanTape` and `TAPERESCUE_DECODER` removed from the environment. Expected values come from `damage.json` and `reference_payloads.json`, which the fixture encoder writes without the decoder.
- Tests, by requirement:
  - Decoder observations: the capture IDs equal `damage.json` `wav_sha256`. In each damaged capture, block 6 has a valid header, a complete 256-byte payload, data CRC outcome `invalid` with recorded value 35417 (0x8A59, equal to `damage.json` `data_crc` and the reference block 6 `data_crc`), and differs from the reference payload exactly at the `damage.json` offsets with the recorded original and damaged values.
  - 14.1: each damaged capture alone gives blocks 0 to 5 and 7 `Intact` and block 6 `CRC failed` with reason `single_read`, no payload and no reconstruction. The gate refuses with blockers `((6, "single_read"),)` and `build_uef` raises `ExportRefused`.
  - 14.2: the intact-only merge (`RecoverOptions(reconstruct=False)`) has anchors 0 to 5 and 7. Block 6 is `CRC failed` with no payload and no reconstruction, the other blocks are `Intact`, `program_payload()` is `None`, and the gate refuses with `((6, "crc_failed"),)`.
  - 14.3: full recovery gives block 6 `Reconstructed · CRC match` and blocks 0 to 5 and 7 `Intact`, final block 7, export permitted with `reconstructed_blocks == (6,)`. Block 6 evaluated 16 of 16 candidates with 1 match. Its payload equals the reference block. The choices are exactly offsets 17, 64, 143 and 201. At each offset the damaged capture observed the `damage.json` damaged value and the other capture observed the original; the chosen value is the original and the only supporting capture is the other one. So 17 and 143 come from capture B and 64 and 201 from capture A.
  - Order: `recover([b, a])` gives byte-identical `dumps_report(build_report(...))` text and `build_uef` bytes to `recover([a, b])`.
  - 14.4: `export_uef` writes the image and `read_uef` (the independent reader) reads blocks 0 to 7 back. The concatenated payload equals the reference block hex joined, is 2025 bytes, has SHA-256 `program_sha256`, and equals `program_payload()`. For every block, both CRCs recompute from the file bytes (`header_crc_ok`, `data_crc_ok`). The header bytes, header CRC and data CRC equal the reference values and also equal the values recorded in the block's observation in both damaged captures. Block 6's data CRC in the file is 35417. The image bytes equal the image exported from `clean.wav` alone.
  - CLI full recovery: `recover A B --report --uef` and `recover B A --report --uef` both exit 0 with empty stderr. Stdout shows block 6 reconstructed, export permitted, the reconstructed-block notice, and the reference `program_sha256`. The two runs give byte-identical report files and byte-identical images, and the images equal the clean-path image. In the report, block statuses are as above, `recovered_payload_sha256` equals the reference, the input digests are the two damaged WAVs, block 6 `recorded_data_crc` is 35417, there are 16 candidates and 1 match, and each choice's `chosen` and `supporting_capture_ids` match `damage.json` (offsets in A sourced from B, offsets in B sourced from A). `verify-uef` on the image exits 0 with `verified: 8 blocks match the reference`. `recover clean.wav --uef` gives the same image bytes and prints `reconstructed blocks in this image: none`.
