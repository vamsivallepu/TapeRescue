## Task 16.1: Two-capture CLI recovery, recovery report, input integrity, and `taperescue demo`
Requirements: 10.7, 10.8, 14.5, 16.1, 16.2, 16.3
### Changes
- `taperescue/cli.py`:
  - `recover A.wav [B.wav] [--intact-only] [--report R.json] [--uef OUT.uef] [--decoder PATH] [--timeout S]`. The task 9.5 rule that rejected a second capture is gone. One or two captures are accepted; three or more is a usage error (exit 2, `error: recover accepts one or two captures (got 3)`). `--intact-only` runs the engine with `RecoverOptions(reconstruct=False)`. `--report` writes `dumps_report(build_report(result, decision))` plus a trailing newline. The report is written before export is attempted, so it exists even when the gate refuses (Requirement 10.8).
  - `export --observations A.json [B.json] -o OUT.uef` accepts one or two observation files under the same rules.
  - `PairingRejected("no_anchor")` maps to `error: These recordings cannot be shown to belong to the same program. Select recordings of the same program version.` with the new exit code **10** (`EXIT_NO_ANCHOR`). No report is written in this case because `recover()` returns no result.
  - Input integrity (Requirement 10.7). `recover`, `export` and `demo` run inside `_inputs_unchanged(paths)`. It hashes every input file with SHA-256 before decoding and again on exit, including when the body raised. A changed or vanished file fails with the new exit code **11** (`EXIT_INPUT_CHANGED`). Python opens inputs only with mode `"rb"`. The decoder reads the WAV through `PcmFile.cpp`, which uses `ifstream(fileName, ios::in | ios::binary | ios::ate)`, so it is read-only as well. An output path (`--uef`, `--report`) that names an input file, or two outputs that name the same file, is a usage error (exit 2).
  - The summary now prints anchors (when there are two captures), the reconstruction mode, and `recovered payload sha256` when every block is recovered. For each block where reconstruction was attempted it prints the candidate, evaluated and match counts. For each differing offset it prints every capture's observed value, plus the chosen value and its source capture when there is one, followed by the CRC-match caveat label. Captures are labelled by file base name when the base names differ, otherwise by the paths as given. Labels appear on stdout only; the report holds no names.
  - Before writing a permitted image, `_export` prints `reconstructed blocks in this image: N, ... (CRC match is evidence, not proof of the original bytes)`, or `none`. This is the CLI counterpart of the Web UI confirmation in Requirement 11.6.
  - `taperescue demo [--out DIR] [--fixtures DIR] [--decoder PATH] [--timeout S]` runs the end-to-end check in one command (Requirement 14.5). It decodes `damaged_a.wav` and `damaged_b.wav` with the real patched decoder. Steps 1 and 2 show each capture alone and the intact-only merge, both leaving block 6 unrecovered with export refused. Step 3 runs full recovery, writes `DIR/report.json`, and exports `DIR/STARMAP.uef`; the exporter verifies the image against the recovery result. Step 4 checks the image with the independent reader against `reference_payloads.json` and prints the payload SHA-256 next to the reference `program_sha256`. `DIR` defaults to `./demo-out`. If any step does not give the expected outcome, the demo exits non-zero: 1 for an unexpected status, 4 for a refused export, 9 for a verification mismatch.
  - The `verify-uef` body is factored into `_verify_against_reference`, which `verify-uef` and `demo` both use. The `verify-uef` output is unchanged.
  - Exit codes 0 to 9 keep their meanings. The table in the module docstring adds 10 and 11.
- `tests/test_cli.py`: the two task 9.5 tests that rejected a second input now check that a third input is rejected. A new section, `two-capture recover, report, input integrity, demo (task 16.1)`, adds these tests:
  - No decoder needed: two synthetic observation files that fail block 1 at different bytes are reconstructed (4 candidates, 1 match), each offset's source is reported, and the reconstructed-block list is printed before `wrote`; the image then passes `verify-uef`. Two unrelated programs exit 10 and write nothing. `_inputs_unchanged` raises exit 11 when a file is modified, and also when the body fails after deleting the input. `--report` equal to the capture, or equal to `--uef`, exits 2. `demo` with a fixtures directory that lacks the WAVs exits 3 and creates nothing.
  - With the decoder (skipped when `build/decoder/ScanTape` is missing): the damaged pair in both orders gives byte-identical reports and UEFs, block 6 is reconstructed with each damaged offset sourced from the other capture (checked against `damage.json`), and the input digests are unchanged. `--intact-only --uef` exits 4 and still writes a report with `reconstruction_enabled: false`, block 6 `CRC failed` with `attempted: false`, and no `recovered_payload_sha256`. A single capture with `--report` exits 0 and its report shows block 6 `CRC failed (single_read)`. `clean.wav` paired with a generated non-STARMAP WAV exits 10 with no report and no image. `demo` passes end to end and leaves the fixture digests unchanged.
