## Task 9.5: Single-capture recover, export, and verify-uef CLI commands
Requirements: 11.2, 16.1, 16.2, 16.3
### Changes
- `taperescue/cli.py`:
  - `recover CAPTURE [--uef OUT.uef] [--decoder PATH] [--timeout S]`. It validates the WAV, decodes it, runs `recover()` and `export_decision()`, and prints one status line per block plus the export decision with its blockers. With `--uef` it calls `export_uef`, which writes the image and then verifies it. When the gate refuses, the command exits 4 and prints `error: export refused: block N: reason`. Without `--uef`, a refused export is reported on stdout and the exit status is 0, so a single capture can still be inspected (Requirement 16.2).
  - `export --observations OBS.json -o OUT.uef`. It loads a document written by `decode`. The `capture_id` must be 64 lowercase hex digits, and the document is validated with `parse_observations` using that ID. The command then runs the same recover, gate and export path. A refusal exits 4. An invalid observations file exits 7.
  - `verify-uef IMAGE.uef --reference reference_payloads.json`. It reads the image with the independent reader (`taperescue.uef.reader`). For each block it checks header CRC and data CRC recompute, block number, payload, `header_raw`, recorded header CRC and recorded data CRC against the reference, and prints one line per block (`ok` or `MISMATCH: ...`). It then compares the block count and the SHA-256 of the concatenated payload with `program_sha256`. Any mismatch, or an image that is not UEF, exits 9.
  - New exit code 9 (`EXIT_VERIFY_FAILED`): the UEF image failed verification, either the post-write check inside `export_uef` or a `verify-uef` mismatch. Codes 0 to 8 are unchanged. Code 4 now applies to `recover --uef` and `export`.
  - `--uef` or `-o` pointing at the input file is a usage error (exit 2). Without this check, the atomic replace would overwrite the capture or the observations file.
  - The decode step is factored into `_decode_wav`, which `decode` and `recover` both use. `decode` behaves as before.
- `tests/test_cli.py`: 16 new tests in the section `recover, export, verify-uef (task 9.5)`.
  - Without the decoder: a second capture is rejected by both `recover` and `export`; `--uef` equal to the capture is rejected; `export` followed by `verify-uef` round-trips on observations built with `block_builder`, which have real CRCs; a refused export prints the blockers, exits 4 and writes no file; invalid observation files (not JSON, bad `capture_id`, wrong schema) exit 7; `verify-uef` flags only the mismatching block and exits 9; a non-UEF image exits 9; a missing reference file exits 1.
  - With the decoder (skipped when `build/decoder/ScanTape` is missing): recovering the clean fixture gives 8 Intact blocks; `verify-uef` matches the reference `program_sha256` with 8 `ok` lines; decode followed by `export --observations` gives the same bytes as `recover --uef`; each damaged fixture exits 4 with block 6 `CRC failed (single_read)` and no file is written; `recover` without `--uef` exits 0 and reports the refusal.
### Decision: second capture
`recover` and `export` take their inputs as a list (`nargs="+"`), so task 16.1 can accept a second capture without changing the interface. For now a second input is rejected with exit 2: `error: recover accepts one capture for now; two-capture recovery is not available yet (got 2)`. `recover()` would accept two captures, but anchors and `PairingRejected` (task 11.1) and reconstruction (task 12.2) are not implemented yet. Accepting a pair now would merge captures that might not belong to the same program.

### Notes
- If `recover --uef` or `export` is refused and a file already exists at the output path from an earlier run, that file is left in place. The command never writes on refusal, and it does not delete files it did not create.
- The summary shows status and reason codes only. The JSON report is task 13. Input digest checks (Requirement 10.7) and `--intact-only` come with task 16.1.
- `export --observations` trusts the `capture_id` in the document because no WAV is available to hash. The ID is checked for format only.
- Loading the clean `.uef` in JSBeeb is still a Pending_Item (manual step).
- Only `taperescue/cli.py`, `tests/test_cli.py` and this entry were changed. Nothing was committed.
