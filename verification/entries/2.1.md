## Task 2.1: Vendor AtomTapeUtils and write the build script
Requirements: 1.1, 1.3, 1.4
### Changes
- `third_party/AtomTapeUtils/`: the 146 tracked files of upstream commit `98d1a8d1bed00aa22f1d72e3d5e91a254a69ec64`, extracted with `git archive` (no `.git` directory), plus `REVISION` containing the full commit id.
- `scripts/build_decoder.sh` (executable): fetch only when the vendored tree is absent, verify the revision, copy to `build/decoder-src/`, `git apply --check` then `git apply`, build the `ScanTape` CMake target, copy the binary to `build/decoder/ScanTape`, and write `build/decoder/BUILD_INFO` (`revision=...`, `patch=none` or patch name and SHA-256).
### Upstream layout compared with the design
- The upstream license file is `LICENSE.txt`, not `LICENSE`. It is the MIT text with the template line `Copyright (c) [year] [fullname]` left unfilled upstream. It is kept byte for byte: SHA-256 `002c2696d92b5c8cf956c11072baa58eaf9f6ade995c031ea635c6a1ee342ad1` for both the upstream checkout and the vendored copy. Task 2.3 and the notices task should check `LICENSE.txt`.
- `gzstream/gzstream.h` and `gzstream/gzstream.cpp` carry their own LGPL-2.1-or-later header (Copyright (C) 2001 Deepak Bandyopadhyay, Lutz Kettner). These are retained unchanged. `ScanTape` links the `gzstream` static library, so `THIRD_PARTY_NOTICES.md` must list it. No other files contain copyright or license text.
- Build system: one top-level `CMakeLists.txt` (UTF-8 with BOM, `cmake_minimum_required 3.8`, C++17, `find_package(ZLIB REQUIRED)`) defining every tool, with `gzstream/` and `shared/` subdirectory libraries. There is no `ScanTape/CMakeLists.txt`. The script builds only `--target ScanTape`.
- Upstream sets `CMAKE_RUNTIME_OUTPUT_DIRECTORY` to `${CMAKE_SOURCE_DIR}/bin`, so the binary lands in `build/decoder-src/bin/ScanTape` and the script copies it to `build/decoder/ScanTape`. The CMake build tree is `build/decoder-build/`.
- All tracked files use LF line endings (`git ls-files --eol`), except `docs/audio.png` (binary). `.gitattributes` is `* text=auto`.
- The script runs `git init` inside `build/decoder-src/`. Without it, `git apply` run there would resolve patch paths against the enclosing TapeRescue repository and skip them as outside the current directory.
### Revision verification
- `REVISION` must equal the pinned commit (or `git rev-parse HEAD` when the vendored tree is a git checkout).
- In addition, the script computes the git tree id of the vendored directory (excluding `REVISION`) in a throwaway bare repository and requires `faf78c9b7ed3cf4a1cd2c2aaabc68716e8ec9f86`, the tree of the pinned commit (`git rev-parse 98d1a8d1...^{tree}`). Any edited, added, or removed file fails with exit 4.
- During vendoring, every vendored file's `git hash-object` was compared with the blob id in `git ls-tree -r` of the pinned commit: 0 mismatches.
### Patch handling
`patches/atomtapeutils-json-observations.patch` does not exist yet (task 2.2). If the patch file is missing, the script exits 6 unless `--unpatched` is given, so an unpatched binary cannot be built by accident once integration work depends on the patch.

Exit codes: 0 success, 1 usage or missing tool, 2 fetch failure, 3 patch does not apply, 4 revision mismatch, 5 build failure, 6 patch missing. Environment overrides for tests: `TAPERESCUE_ATU_URL`, `TAPERESCUE_ATU_VENDOR`, `TAPERESCUE_ATU_PATCH`, `TAPERESCUE_BUILD_DIR`.

### Notes for task 2.2 (line numbers in the pinned `shared/` sources)
- `shared/BlockDecoder.cpp` (403 lines): `bool BlockDecoder::readBlock(BlockTiming blockTiming, bool firstBlock, FileBlock& readBlock, bool& leadToneDetected, BlockError& readStatus)` spans lines 86–356.
  - Lines 116–127: carrier wait (returns false at lines 121 and 126). The first BBC block uses `waitForCarrierWithDummyByte`, which expects prelude tone, then a dummy byte, then the lead tone. Return false here means `leadToneDetected == false`.
  - Lines 141–149: `0x2A` sync byte through `checkBytes` (return false at line 148). Lines 158–165: `getBlockName`, the name plus terminator, added to the CRC. Lines 167–179: rest of header through `mReader.readBytes(hdr_bytes, readBlock.tapeHdrSz(), n_read_bytes)`. Line 182: `decodeTapeBlockHdr(name_bytes, hdr_bytes, mLimitBlockNo)`. `name_bytes + hdr_bytes` is the design's `header_raw`.
  - Lines 191–218: header CRC. If `getWord(&hdr_CRC)` fails (line 195), the function returns false at line 198 (header CRC `unreadable`). A mismatch (line 203) sets `BLOCK_HDR_CRC_ERR` and does **not** abort, so data is still read after an invalid header CRC.
  - Lines 237–251: data. `mReader.readBytes(readBlock.data, block_len, n_read_bytes)` (line 239). `TapeReader::readBytes` (`shared/TapeReader.cpp` lines 6–18) appends each byte as it is read, so on failure `readBlock.data` holds the bytes read so far (the truncated case). The function then returns false at line 243.
  - Lines 259–280: data CRC. For BBC with `block_len > 0`, `getWord(&data_CRC)` (line 264). On failure it returns false at line 267 (data CRC `unreadable`, with the full payload already in `readBlock.data`). Upstream quirk: for a BBC block with `block_len == 0` the `else` branch (lines 271–280) still reads one byte with `readByte` and returns false at line 276 if that fails, although no CRC is checked. This matters for empty-payload handling.
  - Lines 283–291: a data CRC mismatch sets `BLOCK_DATA_CRC_ERR` and does **not** abort. The full payload and recorded CRC are both available. This is the damaged block 6 case (Requirement 2.3).
  - Lines 300–316: for the last BBC block (return false at line 308), the function requires a trailer tone of at least `minBlockTiming.trailerToneDuration` (0.5 s) and **returns false if none is found**, after the data CRC was read. A hook placed only on the success path would drop a fully read last block.
  - Natural hook points: one emit call before each `return false` after line 127 (with the partial state), and one after line 291 (CRC outcomes known), or a single emit in a wrapper around `readBlock` that uses `readBlock`, `readStatus`, and captured CRC values.
- `shared/FileDecoder.cpp` (384 lines): `bool FileDecoder::readFile(ostream& logFile, TapeFile& tapFile, string searchName, FileReadStatus &readStatus)` starts at line 43. It calls `mBlockDecoder.readBlock(...)` at line 112, computes `complete_block` at line 157, and zero-pads at lines 204–222 (`read_block.data.push_back(0x0)` at line 220). Observations must be taken before line 112 returns to this function, which means inside `BlockDecoder::readBlock`.
- Also noted for the fixture encoder (task 6.x): `shared/TapeProperties.h` lines 104–109 define `bbmTiming` with minimum timings (first-block prelude 3 cycles, first-block lead 2.0 s, other-block lead 0.2 s, trailer 0.5 s) and nominal timings (4 cycles, 5.1 s, 0.9 s, trailer 5.3 s, last-block gap 1.8 s). The first BBC block expects a dummy byte between the prelude and the lead tone (comment at lines 73–74 of `BlockDecoder.cpp`).
- `ScanTape/ArgParser.cpp`: options are parsed in a `strcmp` chain from line 94 (`-bbm` pre-scan at line 83, main-loop entry at line 129). Usage text is at lines 22–52. The new `-json` and `-capture-id` options go into this chain.
