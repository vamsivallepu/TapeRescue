## Task 4.1: WAV validation (`taperescue/wavcheck.py`)
Requirements: 3.1, 3.2, 3.3
### Changes
- `taperescue/wavcheck.py`: `WavInfo`, `WavRejected(code, message)` with codes `not_riff_wave`, `unsupported_format`, `too_large`, `too_long`, `no_data`, constants `MAX_BYTES = 64 MiB` and `MAX_SECONDS = 600`, `inspect_wav_header(head, file_size)` and `validate_capture(path)`.
- The RIFF chunk list is walked directly, with odd-size padding handled and unknown chunks skipped. The file extension is not used. Accepted: format tag 1 (PCM), or `WAVE_FORMAT_EXTENSIBLE` (0xFFFE) whose sub-format GUID is the PCM GUID. The sample rate must be 44100 Hz, the samples 16-bit, the channel count 1, and the block align consistent with them.
- Check order: size (before any parsing), RIFF/WAVE magic and fmt chunk, format, data presence, then duration = `data_bytes / (sample_rate * block_align)`. Exactly 64 MiB and exactly 600 s are accepted.
- A data chunk size that extends past the end of the file is clamped to the bytes actually present.
- `validate_capture` opens the file read-only and seeks between chunk headers. It does not read the samples.
- Example rejection message: `Detected PCM, 48000 Hz, 16-bit, 2 channels; TapeRescue supports 44100 Hz, 16-bit, mono PCM`. The size and duration messages state the limit (`64 MiB (67108864 bytes)`, `10 minutes (600 s)`) and the detected value.
- `tests/test_wavcheck.py`: 26 unit tests that build WAVs in memory with `wave` and `struct`. They cover acceptance of plain PCM and of extensible PCM, chunk walking, header-only input, and the 600 s and 64 MiB boundaries. They also cover each rejection code: not RIFF/WAVE (5 inputs), unsupported format (rate, 8/24-bit, stereo, IEEE float, extensible with a non-PCM GUID or with no extension), too large (in memory, and as a sparse file on disk), too long, and no data (3 inputs).
