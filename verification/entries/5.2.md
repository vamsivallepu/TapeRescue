## Task 5.2: Implement `taperescue/decoder_adapter/run.py`
Requirements: 1.5, 3.4, 3.5
### Changes
- `taperescue/decoder_adapter/run.py` (new):
  - `capture_id_for(path)`: lowercase SHA-256 hex of the file bytes, read in 1 MiB chunks.
  - `decoder_args(decoder, wav, out, capture_id) -> list[str]`: builds the argument list.
  - `decode_capture(wav, *, decoder, workdir, timeout_s=60.0) -> CaptureObservations`: resolves the paths, computes the capture ID, generates `out = workdir/observations-<uuid4 hex>.json`, and calls `subprocess.run(args, shell=False, timeout=timeout_s, capture_output=True, cwd=workdir, stdin=DEVNULL)`. After the decoder exits it reads `out`, parses it with `schema.parse_observations`, and removes `out` and `out.tmp` in a `finally` block.
  - `NO_BLOCKS_MESSAGE = "No BBC 1200-baud blocks were found in this capture"`.
  - `DecoderError` and `parse_observations` are imported from `schema.py`, not redefined.
- `taperescue/decoder_adapter/__init__.py`: re-exports `DecoderError`, `parse_observations`, `capture_id_for`, `decode_capture`, `decoder_args`, `NO_BLOCKS_MESSAGE`.
### Deviation: argument order
The task lists `[decoder, "-bbm", "-json", out, "-capture-id", cid, wav]`. Upstream `ScanTape/ArgParser.cpp` reads the input file from `argv[1]` (line 71) and starts option parsing at `argv[2]`, so that order fails: the decoder exits 255 with `WAV file '-bbm' cannot be opened!` on stdout and writes no JSON (checked below). `run.py` uses the order the patch accepts, the same one used in task 2.2:

```
[decoder, wav, "-bbm", "-json", out, "-capture-id", cid]
```

Because the WAV is `argv[1]` and is passed as an absolute path, a file name that starts with `-` cannot be read as an option.
### Error mapping
| Condition | `DecoderError.code` | `message` | `detail` |
| --- | --- | --- | --- |
| `subprocess.TimeoutExpired` (`subprocess.run` kills the child) | `timeout` | `Decoding timed out after 60 s` (uses `timeout_s`) | none |
| Decoder binary cannot be started (`OSError`) | `decoder_failed` | `Decoder failed on this capture` | OS error text |
| Non-zero exit | `decoder_failed` | `Decoder failed on this capture` | `exit status N: <stderr, or stdout if stderr is empty, truncated to 2 KB>`, which is also logged at WARNING |
| Output file missing or unreadable, or not JSON | `invalid_output` | `Decoder output was invalid for capture <id>: ...` | reason |
| Schema violation | `invalid_output` (raised by `parse_observations`) | as in task 5.1 | rule |
| No observation with `header_crc.outcome == "valid"` | `no_blocks` | `No BBC 1200-baud blocks were found in this capture` | none |

Notes:
- The stdout fallback is there because upstream ScanTape prints some input errors to stdout, for example `Input file has no data or is not a valid 8 or 16-bit PCM Wave file!`. The user-facing message stays generic, as in the design's error table.
- Schema validation runs before the `no_blocks` check, so a malformed document is reported as `invalid_output` even when it has no blocks.
- A document whose blocks all have invalid or unreadable header CRCs gives `no_blocks` (Requirement 3.5 says "no valid block header").
- `decode_capture` does not call `wavcheck.validate_capture`. Callers (CLI and API) validate first, following the design's pipeline.
