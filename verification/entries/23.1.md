## Task 23.1: Create the recovery test hook
Requirements: 20.1, 20.2
### Changes
- `.kiro/hooks/recovery-tests.json` (new). One hook in the v1 format used by `.kiro/hooks/auto-commit-docs-on-major-change.json` (`version`, `hooks[]` with `name`, `trigger`, `description`, `action`), plus `matcher` and `timeout`:
  - `trigger`: `PostFileSave`
  - `matcher`: `(^|/)taperescue/(decoder_adapter|engine)/.+\.py$` (regex against the saved file path; matches relative and absolute paths, including subdirectories)
  - `action`: `{"type": "command", "command": ".venv/bin/python -m pytest tests/engine tests/decoder_adapter tests/integration -q && .venv/bin/python -m pytest tests/properties -q"}`
  - `timeout`: 180 seconds (the default is 60; the command takes about 40 s)
- `.kiro/hooks/auto-commit-docs-on-major-change.json` was not modified (`git diff --stat` on it is empty).

### Schema source
[Kiro hooks overview](https://kiro.dev/docs/hooks/) and [Hook triggers](https://kiro.dev/docs/hooks/types/), fetched during this task. The overview gives the v1 schema: `hooks[].trigger` (PascalCase), optional `matcher` (for file events, a regex against the file path), `action.type` `"command"` or `"agent"`, `action.command` for command actions, optional `timeout` in seconds (default 60). Command actions run in the project root and receive the event JSON on STDIN. The trigger names in the task text (`PostFileSave`, `matcher`) match the documented schema, so no renaming was needed. A command action was chosen over an agent prompt so the tests run directly instead of asking the agent to run them.

### Choice of test directories
The design names `tests/engine tests/decoder_adapter`. Coverage of the matched source was checked with `grep` for imports of `taperescue.engine` and `taperescue.decoder_adapter` under `tests/`:
- `tests/engine` (8 files): engine unit and acceptance tests. Included.
- `tests/decoder_adapter/test_schema.py`: schema validation only. Included.
- `tests/integration` (3 files): the only tests that run `taperescue/decoder_adapter/run.py` (`decode_capture` with the built `ScanTape`, truncated-WAV and silent-WAV cases in `test_fixture_decode.py`), plus the clean-fixture UEF path and the STARMAP end-to-end recovery through the engine. Included, so a change to `run.py` is actually exercised. These skip with a message if `build/decoder/ScanTape` is missing.
- `tests/properties` (6 files): every file imports `taperescue.engine` (recover, reconstruct, gate, report). Included.
- Not included: `tests/server`, `tests/smoke` and the top-level `tests/test_*.py` files. They test the server, CLI, fixture encoder, UEF and WAV checks, which are outside the matched directories.

### Pre-existing finding: property generator-coverage checks depend on which tests run together
A single pytest run over the chosen directories fails one generator-coverage test, while the same test passes alone, with `tests/properties` alone, and in the full suite. Hypothesis is 6.170.17.
| Command | Result |
| --- | --- |
| `.venv/bin/python -m pytest tests/engine tests/decoder_adapter tests/properties tests/integration -q` | `1 failed, 190 passed in 40.86s`: `test_prop_order_independence.py::test_generator_reaches_interesting_cases`, `('status:Missing', ...) assert 4 >= 5`. Reproduced on a second run |
| `.venv/bin/python -m pytest tests/engine tests/decoder_adapter tests/properties -q` | `1 failed, 159 passed in 39.29s`: `test_prop_uef_roundtrip.py::test_generator_covers_the_cases` |
| `.venv/bin/python -m pytest tests/properties/test_prop_order_independence.py::test_generator_reaches_interesting_cases -q` | `1 passed in 3.41s` |
| `.venv/bin/python -m pytest tests/properties -q` | `15 passed in 36.39s` |
| `.venv/bin/python -m pytest -q` | `489 passed, 1 warning in 46.18s` |

Both failing tests use `derandomize=True` with fixed minimum counts per case. The likely cause is that this Hypothesis version mixes constants collected from the imported local modules into generation (the `.hypothesis/constants/` directory), so the derandomized sample changes with the set of modules loaded. That cause has not been confirmed. The tests and the engine were not changed in this task. The hook runs `tests/properties` in its own pytest invocation, which passes and is deterministic on the current code.
