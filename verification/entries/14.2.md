## Task 14.2: Property test for UEF round trip (Property 22)
Requirements: 11.3, 11.4, 13.5
### Changes
- `tests/properties/test_prop_uef_roundtrip.py` (new). No exporter, verifier, reader or engine code changed: no product bug was found.
  - Tag: `# Feature: tape-rescue, Property 22: UEF export round trip with recorded CRCs`, plus the module docstring with **Validates: Requirements 11.3, 11.4, 13.5**.
  - Settings: `max_examples=300`, `derandomize=True`, `deadline=None`. Strategies are local to the file.
  - Header bytes, header CRCs and data CRCs are built in the test with a local bitwise CRC-16/XMODEM. The test imports neither `taperescue.crc` nor the reader's CRC routine, so expected values do not come from a component under test.
  - Generator `sessions()`:
    - Block count 1 to 9 drawn first, then a program length in that block range (up to 2300 bytes) or an exact multiple of 256. A multiple of 256 is sometimes followed by an empty final block (flags `0xC0`, no data CRC). Program bytes come from a seeded `random.Random`. Random filename (1 to 10 chars), load and exec addresses, and an optional locked bit.
    - One capture (all blocks intact) or two captures with distinct 64-hex IDs. With two captures: one anchor block intact in both; other blocks intact in both, intact in one and bit-damaged (1 to 3 single-bit flips, data CRC `invalid`, original CRC recorded) or absent in the other. In about half of two-capture sessions one block of 2 or more bytes is damaged in both captures at disjoint offsets (at most 64 candidates), so the engine must reconstruct it.
    - Each capture has its own next-file address, so the two captures' header bytes and header CRCs usually differ and the exporter's choice of source read shows in the file.
    - Up to three invalid-header reads placed before a valid read of the same block. They have one bit flipped in the next-file address, the header CRC of the good header (outcome `invalid`) and random payload bytes, which must never reach the image.
    - Reads are shuffled within each capture and captures are permuted.
  - `test_uef_export_round_trip_with_recorded_crcs`: `recover` -> `export_decision` (must be permitted; the reconstructed block must be `Reconstructed · CRC match`, and a `multiple_matches` CRC collision is discarded with `assume`) -> `export_uef` into a temporary directory -> `read_uef`. It checks:
    - The directory holds only the output file.
    - The file holds one block per generated block, with block number `n` and flag bit 7 only on the last block.
    - Header bytes equal the lowest-`(capture_id, sample_offset)` valid-header observation. The header CRC in the file equals that observation's recorded header CRC.
    - Payloads equal the generated payloads.
    - The data CRC in the file equals the recorded data CRC of the source observation (first intact read of the payload, or for a reconstructed block the first complete read with a readable CRC). It is one of the values the block's valid-header observations recorded. All of those equal the CRC of the original payload, which checks the generator.
    - An empty block has no data CRC in the file and none recorded.
    - `header_crc_ok` and `data_crc_ok` are true, and the local CRC recomputed from the file bytes matches both CRCs in the file.
    - The concatenated payload equals the program and `result.program_payload()`.
  - `test_tampered_recorded_crc_fails_verification`: takes the same sessions and XORs a non-zero delta into either the recorded header CRC of the header source read or the recorded data CRC of the data-CRC source read (not on the reconstructed block, where differing CRCs would make the engine refuse it first). The outcome stays `valid`. It checks:
    - The gate still permits export.
    - The image from `build_uef` carries the tampered value, so the exporter writes recorded CRCs and does not recompute them.
    - `export_uef` raises `ExportVerificationFailed` with a problem naming that block.
    - The temporary directory is empty afterwards, so neither the output nor a temporary file remains.
  - `test_generator_covers_the_cases`: a fixed 200-example sample must contain at least 40 one-capture and 40 two-capture sessions, 20 with a reconstructed block, 10 with an empty final block, 10 with 8 or more blocks, 20 with invalid-header reads, and 20 two-capture sessions whose block 0 header bytes differ between captures.
