## Task 9.4: UEF exporter and export verification
Requirements: 11.3, 11.4
### Changes
- `taperescue/uef/exporter.py` (new):
  - `export_uef(result, decision, out)`, following the design signature. It calls `build_uef`, writes the image atomically (`tempfile.mkstemp` in the output directory, then `fsync` and `os.replace`, and the temp file is removed on error), and then calls `verify_export(out, result)`.
  - `build_uef(result, decision=None) -> bytes`. It refuses with `ExportRefused(blockers)` if the passed decision is not permitted, and also if `export_decision(result)` is not permitted. A stale permitted decision therefore cannot unlock a bad result. Nothing is written when export is refused.
  - `ExportRefused(blockers)` holds `.blockers` as sorted `(block_no, reason)` pairs, the same as the gate's.
  - Layout: `UEF File!\0`, minor 10, major 0, then chunk `0x0000` origin `TapeRescue <version>\0`. For each block `0..final` there is a `0x0110` carrier chunk and then a `0x0100` chunk containing `0x2A`, `header_raw`, the header CRC (high byte first), the payload, and the data CRC (high byte first). An empty block has no payload and no data CRC. A trailing `0x0110` follows the last block. Following the design, there is no `0xAA` dummy byte.
  - Source bytes. The header bytes and header CRC come from the valid-header read with the lowest `(capture_id, sample_offset)`, the same read the gate checks. The data CRC is the recorded value of the first such read that is intact with the selected payload. If no read is intact, it comes from the first complete read with a readable recorded CRC (the reconstructed-block case). If no recorded data CRC exists, the exporter raises `ExportRefused([(n, "crc_unreadable")])`. The payload is `BlockResult.payload`.
  - The exporter never computes a CRC. It does not import `taperescue.crc` or the reader.
- `taperescue/uef/verify.py` (new):
  - `verify_export(path, result)` and `ExportVerificationFailed(problems)`. It imports only `taperescue.models` and `taperescue.uef.reader`, not the exporter or `taperescue.crc`, so it works out the expected values itself.
  - Checks, all run with the independent reader:
    - The file holds exactly `final + 1` blocks.
    - Each block's header bytes and header CRC equal those of the lowest-ID valid-header read.
    - `header_crc_ok` is true.
    - The payload equals the selected payload.
    - A non-empty block's data CRC is one recorded by a valid-header read of that block, and `data_crc_ok` is true.
    - An empty block has no data CRC.
    - The concatenated payload equals `result.program_payload()`.
    - An unreadable or malformed file is also a failure.
  - On any failure it deletes the file (`unlink(missing_ok=True)`) and raises an exception that lists every problem.
- `tests/test_uef_exporter.py` (new, 13 tests). The observations are byte arrays built with `block_builder`, so the CRCs are real. The tests cover:
  - Single-capture round trip through `read_uef`, with no temp file left behind.
  - Image layout: magic and version, the origin chunk, carrier values `[12240, 2160, 2160, 2160, 4800]`, chunk order, and the exact `0x0100` bytes.
  - An empty block (flags `0xC0`) with no data CRC.
  - Two captures whose headers differ only in the next-file address. The A header is used for every block, including a block that is intact only in B, and the result is the same in both input orders.
  - A hand-built Reconstructed block. Its written data CRC is the original value recorded on the failed reads.
  - Refused export (`single_read` blocker) writes nothing.
  - A stale decision is refused in both directions.
  - Tampered recorded CRC: the observation claims a valid data CRC, but the recorded value is the real CRC XOR 1. `build_uef` writes the tampered value unchanged, and `export_uef` raises `ExportVerificationFailed` and leaves no file.
  - A payload bit flipped in the file after export makes verification fail and deletes the file.
  - A self-consistent image with CRCs that were not recorded in the captures is rejected.
  - A non-UEF file is rejected and deleted.
  - AST import checks: the exporter has no `taperescue.crc`, reader, `zlib`, `binascii` or `crc16`, and verify does not import the exporter or `crc`.
### Decision: carrier tone lengths
- Source: fileformats.org, "UEF file format: Chunks" (https://fileformats.org/system/floppy/uef/chunks/). Its table is checked against the UEF specification 0.10 (draft 28), the EmWare reader, and a real BeebEm tape. It describes chunk `&0110` as a 16-bit count of cycles at twice the base frequency, which is 2400 Hz at the default 1200 Hz base frequency. The TomHarte/CLK wiki page returned no content when fetched.
- Decision: write the counts in the spec's unit, using the BBC MOS durations already used by `taperescue.fixtures.fsk.BBC_TIMING`:
  - 12240 cycles (5.1 s) before block 0
  - 2160 cycles (0.9 s) before the other blocks
  - 4800 cycles (2.0 s) trailing, the same as the fixture trailer
- This departs from the design's numbers. The design's "5100 / 1800 cycles" would be 2.125 s / 0.75 s in the spec's unit, so I read it as the intended 5.1 s / 0.9 s with the unit mixed up. Both sets of values fit in 16 bits, and either should load, because emulators only need enough leader to detect carrier. The constants are `FIRST_CARRIER_CYCLES`, `OTHER_CARRIER_CYCLES` and `TRAILING_CARRIER_CYCLES` in `exporter.py`.

### Notes
- `export_uef` always runs `verify_export` after writing, which is how the design's error table describes it ("post-write verification fails: delete the output, raise `ExportVerificationFailed`"). If verification fails after an existing file at `out` was replaced, that file is gone too.
- Loading in an emulator (JSBeeb) has not been checked. It stays a Pending_Item for the clean and recovered `.uef` (task 9.6 and the manual steps).
- No property test was added. Property 22 (UEF round trip) is task 14.2.
- Only `taperescue/uef/exporter.py`, `taperescue/uef/verify.py`, `tests/test_uef_exporter.py` and this entry were added. Nothing was committed.
