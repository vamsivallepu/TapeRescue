### Field semantics (for task 5.1 and task 8)
- `sample_offset` is the sample index where the level decoder detects the start bit of the block's `0x2a` sync byte, and `time_s` is the same position in seconds (`%.6f`). On synthetic WAVs it was 1 sample after the computed start of the start bit, for all 9 blocks checked.
- `header_raw` covers the filename bytes, including the `0x00` terminator, through the next-file address. It excludes the sync byte and the header CRC. A partly read header keeps the bytes that were read.
- `header` holds the parsed fields only when the header CRC is `valid`. Otherwise it is `null`, which matches `models.py` ("None when the header CRC is not valid"). The fields are parsed from `header_raw`: `block_len` is the raw 16-bit length field and `flags` is the raw flag byte.
- `expected_len` is `readBlock.size`, the payload length the decoder tried to read. It is 0 when the header could not be fully read and decoded.
  - Edge case: upstream `updateFromBBMFlags` forces the size to 0 when flag bit 6 (empty block) is set. A header with bit 6 set and a non-zero length field would therefore give `expected_len = 0` with `header.block_len != 0`. The project Block_Builder does not produce such headers.
- `data_crc` is `null` when the header was decoded and `expected_len == 0`, because the BBC format has no data CRC for an empty block. Otherwise it is `{"outcome": "valid"|"invalid", "recorded": n}`, or `{"outcome": "unreadable"}` with no `recorded` key when the CRC bytes were not read. The same rule applies to `header_crc`.
- `actual_len` equals `len(payload)` and is never more than `expected_len`. A data or header CRC mismatch does not stop reading (upstream behaviour), so the full payload and the recorded CRC are both emitted.
- Blocks are written in sample-offset order. A block re-read after a `FileDecoder` rollback (a block from another file found while reading a file) has the same sample offset and replaces the earlier entry. The `rollback.wav` case below has no duplicates.
### Deviation: end-of-samples fix in `WavCycleDecoder::countHalfCycles`
The first build (before this fix) failed 2 of 95 checks. If a capture ended inside a byte frame, upstream `countHalfCycles` stopped at the end of the samples and still returned true. The missing bits then decoded as `1`, and a byte that was never recorded came back as read:
- A cut 2 to 7 bits into payload byte 101 gave `actual_len = 101`, with a last byte of `ff`, `fd`, `f5`, or `c5` against a recorded `85`.
- A cut inside the second data CRC byte gave `data_crc {"outcome": "invalid", "recorded": 0x53f3}` against a recorded `0x5393`, where the correct result is `unreadable`.

That violates Requirement 2.4 (emit only the bytes actually read) and Requirement 2.7 (an unreadable CRC is `unreadable`). The fix returns false when the bit window is cut off. The `getDataBit` caller already treats false as "unexpected end of samples". After the fix:
- A cut 0 to 9 bits into byte 101 gives `actual_len = 100`, with every byte equal to what was written. A byte whose stop bit is missing is dropped, which is the conservative choice.
- A cut 10 bits in (the full frame) gives 101, and a cut 20 bits in gives 102.

Effect on the stock (non-JSON) behaviour: on `trunc_crc.wav`, `-c` output now reports 1 complete block where stock reported 2, because stock had read the data CRC from missing samples. On the other 4 synthetic WAVs, the `-c` output was byte-identical to the stock decoder. On `multi.wav`, the `-g` output directory (`tape.log`, `.bbc`, `.dat`, `.inf`, `.tap`, `.uef`, bin) was identical to stock.
