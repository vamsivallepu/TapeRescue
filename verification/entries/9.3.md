## Task 9.3: Independent UEF reader
Requirements: 11.4
### Changes
- `taperescue/uef/reader.py`:
  - `UefBlock` (frozen dataclass with the design fields `header_raw`, `header_crc_in_file`, `payload`, `data_crc_in_file`, `header_crc_ok`, `data_crc_ok`). It also has read-only properties `filename`, `load_addr`, `exec_addr`, `block_no`, `block_len`, `flags` and `next_addr`, which are parsed from `header_raw`.
  - `read_uef(path)` and `parse_uef(data)`. Both accept plain or gzip UEF, including gzip files with several members.
  - `UefFormatError(ValueError)`.
  - `_crc16_xmodem_bitwise`, a bitwise CRC-16/XMODEM (poly 0x1021, init 0, no reflection, no final XOR).
- The reader imports only the standard library (`gzip`, `struct`, `zlib`, `dataclasses`, `pathlib`). It imports nothing from `taperescue`, so it shares no code with `taperescue.crc` or `taperescue.uef.exporter`. A test checks this with an AST walk of the module.
- Container parsing: the reader checks the 10-byte `UEF File!\0` signature, skips the minor and major version bytes, and then walks chunks of `<id u16 LE><length u32 LE><data>`. A chunk header or chunk body cut short raises `UefFormatError`.
- Only chunk `0x0100` is read. All other chunks are skipped by their length, including unknown IDs. The data of all `0x0100` chunks is joined in file order, so a block split across several `0x0100` chunks (with other chunks between them) is parsed as one block.
- Block parsing: bytes before a `0x2A` are skipped, for example the `0xAA` dummy byte. After a `0x2A` the reader reads a 1–10 byte filename and its NUL, then 17 header bytes (load, exec, block number, length, flags, next address, all LE), then the header CRC (high byte first). It then reads `length` data bytes and a data CRC (high byte first). When the length is 0 there is no data and no data CRC: `data_crc_in_file` is None and `data_crc_ok` is True.
- The reader reports the CRC values stored in the file, and `*_ok` says whether each one recomputes from the file bytes. A block with a bad header CRC is still consumed using its length field, and the reader reports `header_crc_ok=False`.
- Errors raised as `UefFormatError`: missing signature, header shorter than 12 bytes, truncated chunk, corrupt gzip, `0x2A` without a NUL-terminated 1–10 byte name, empty filename, header or data+CRC cut short.
- `tests/test_uef_reader.py`: 26 unit tests, all on hand-built UEF bytes (the exporter does not exist yet). They cover:
  - CRC check values `123456789` → 0x31C3 and Test_Payload → 0xAC93, and agreement with `taperescue.crc`.
  - A plain two-block image.
  - High-byte-first CRC order.
  - A gzip image and a multi-member gzip image.
  - Unknown chunks and a dummy `0xAA` byte.
  - A block split across three `0x0100` chunks with a tone chunk between them.
  - `0x2A` bytes inside a payload, which must not cause a resync.
  - A bad data CRC, a flipped payload bit, and a bad header CRC.
  - An empty block with flags `0xC0`, and a 10-character filename.
  - An image with no tape data, and reading from a file.
  - Nine malformed inputs.
  - Import independence.

### Format sources
- Block layout, CRC coverage and byte order: fileformats.org, "UEF file format: Cassette blocks" (https://fileformats.org/system/floppy/uef/blocks/). That page bases its table on BeebWiki's "Acorn cassette format" page and checks it against the CRCs of a real tape. It gives:
  - Sync `$2A`, then a 1–10 byte name and `$00`.
  - Load and exec addresses low byte first, block number 2 bytes, length 2 bytes, flag (bit 7 last block, bit 6 empty, bit 0 locked), next-file address 4 bytes.
  - Header CRC high byte first, covering the name with its `$00` through the spare bytes.
  - Data, then data CRC high byte first, with no data CRC when the length is 0.
  - The CRC is XMODEM with check value $31C3.
  - The BeebWiki page itself (https://beebwiki.mdfs.net/Acorn_cassette_format) timed out when fetched.
- Container: fileformats.org, "UEF file format" (https://fileformats.org/system/floppy/uef/). It gives:
  - Usually gzip, possibly multi-member, and plain is also valid.
  - `UEF File!` and `$00`, then minor and major version bytes.
  - Chunks of a 16-bit type and a 32-bit length, both little-endian.
  - That page cites the UEF specification 0.10, draft 28.
- Cross-check against the vendored source:
  - `third_party/AtomTapeUtils/shared/BBMBlockTypes.h` gives the same header layout and offsets (block length at offset 10 after the name, flags at 12, next address at 13).
  - `shared/UEFCodec.cpp` (lines 196–236) writes the `0x2A` preamble, starts the header CRC at the filename, and writes CRCs as `crc / 256` then `crc % 256` (high byte first).

### Blockers
None. Notes and limitations:
- The reader reads only `0x0100` chunks, as the design specifies, and the TapeRescue exporter will write only `0x0100`. AtomTapeUtils' own UEF writer (`UEFCodec.cpp`) writes block headers and data as `0x0104` chunks (8N1) and only the preamble and CRCs as `0x0100`. This reader cannot parse UEF files from that writer, and it raises `UefFormatError` or misreads them. Supporting `0x0104` with 8N1 is possible later if third-party images need to be read.
- The reader does not enforce the 256-byte block maximum or block sequencing. Comparing against the recovery result belongs to `verify_export` (task 9.4).
- No exporter round-trip test exists yet. That belongs to tasks 9.4 and 9.6, and to Property 22.
